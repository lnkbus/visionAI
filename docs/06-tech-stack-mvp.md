### 알려진 제약

- **`memory` 벡터 저장소는 단일 프로세스 전용이다.** RAG-KB와 RAG-SRCH를 별도
  컨테이너로 띄우면 색인한 문서가 검색에 보이지 않는다. 다중 컨테이너 배포에는
  Qdrant를 쓴다(compose 기본값). 오설정 시 기동 로그에 경고가 남는다.
- **BM25 색인은 메모리 상주다.** 프로세스 재시작 시 `VAI_SRCH_WARM_TENANTS`
  또는 `/internal/v1/kb/{kb}/rebuild`로 복원해야 한다. 복원하지 않으면 검색이
  밀집 축만으로 도는 "절반만 동작하는" 상태가 되는데, 장애로 보이지 않아 더 위험하다.
- **한국어 토큰화는 어절 + 음절 바이그램**이다. 형태소 분석기(kiwi/mecab)는
  평가셋으로 이득을 측정한 뒤 어댑터로 교체한다. 검색 질의 확장, 추천 답변
  근거 검증, 음성봇 의도 분류가 모두 이 토크나이저 위에 있다 — 교체하면
  세 곳의 임계값을 함께 재조정해야 한다.
- **음성봇 sLLM 의도 분류는 기본 꺼짐이다**(`VAI_BOT_CLASSIFY_SLM`). 어휘
  분류만으로 골든셋 0.900에 도달했고, 그 위를 sLLM이 얼마나 올리는지는
  가중치가 있어야 잴 수 있다. 재현되지 않는 수치는 회귀 게이트에 넣지 않는다.
- **추천 답변의 근거 검증은 어휘 수준이다.** 인용 표기·숫자 일치·확약 표현·어휘
  일치율까지 본다(§5.3). 문장 단위 함의(NLI) 판정은 없어서, **숫자가 없고 짧은
  왜곡**은 통과할 수 있다("우편으로도 신청하실 수 있습니다"). 골든셋에 알려진
  한계로 고정해 두었다.
- **추천 답변은 실제 sLLM으로 검증되지 않았다.** 검증기·폴백·지연 분리는
  실행으로 확인했지만, 어떤 모델이 어느 정도 비율로 검증을 통과하는지는
  가중치가 있어야 잴 수 있다. echo 어댑터는 인용을 못 만들어 전부 폐기되며,
  이는 **모델이 없으면 답변이 안 뜬다**는 올바른 동작이다.
- **기본 화자 임베더(spectral)는 음역이 뚜렷이 다른 화자만 가른다.** 같은 성별의
  비슷한 목소리는 한 사람으로 뭉친다. 회의록 품질이 필요한 고객사는 반드시
  신경망 임베더(ECAPA-TDNN 계열)를 쓴다 — 어댑터 교체만으로 되지만
  **유사도 임계값을 재조정해야 한다**(임베더마다 유사도 분포가 다르다).
- **화자분리는 온라인 방식이라 후처리 재군집화가 없다.** 회의 초반에 갈린
  화자가 후반에 같은 사람으로 밝혀져도 되돌리지 않는다. 오프라인 배치
  재군집화(회의 종료 후 전체 재계산)는 정확도가 높지만 미구현이다.
- **SIP 시그널링은 구현하지 않았다.** 고객사마다 미디어를 받는 방식이 다르다
  (SIPREC 복제 / 미디어 게이트웨이 / CTI 이벤트). 어느 하나를 가정해 SIP UA를
  만들면 대부분의 고객사에서 못 쓰는 코드가 되므로, **제어 API**(`/internal/v1/calls`)를
  열어 두고 시그널링 어댑터는 구축 시 고객사 환경에 맞춰 붙인다.
- **RTCP는 처리하지 않는다.** 홀수 포트는 관례대로 비워 두지만 수신·해석은
  하지 않는다. 통화 품질 지표는 RTP 수신 통계로만 산출한다.
- **손실 은닉(PLC)이 없다.** 유실 구간은 무음으로 채운다. G.711에 PLC가 없어
  이게 표준적인 최소 처리이며, 손실률이 높은 망에서는 인식률이 떨어진다.
- **시나리오 흐름 저작은 미구현이다.** SCN-STUDIO는 현재 컴플라이언스 룰 저작만
  제공한다. 분기·조건·기간계 액션 호출을 담는 흐름 에디터와 시뮬레이터는
  BOT-VOICE(Wave 7)와 함께 설계해야 중복 없이 만들 수 있다.
- **아바타 렌더러는 데모 수준이다.** SVG 타원 하나로 입을 그린다. 실제 제품은
  3D 모델의 블렌드셰이프에 같은 viseme 가중치를 먹이면 되지만, 모델 제작과
  표정·제스처는 이 저장소 범위 밖이다(고객사 브랜드에 맞춰 제작).
- **입 모양은 음절 균등 분배다.** TTS가 음소 단위 타임스탬프를 주면 훨씬
  정확해진다. CosyVoice·Kokoro가 그 정보를 노출하면 어댑터에서 받아 쓰도록
  계약(`VisemeFrame`)은 열어 두었다.
- **감정·표정 표현이 없다.** ``VoiceStyle``은 목소리에만 적용되고 얼굴에는
  반영되지 않는다. 민원 응대에서 밝은 표정은 역효과라 신중히 설계할 부분이다.
- **TTS는 fake 어댑터로만 검증됐다.** CosyVoice·Kokoro 연동은 배선돼 있으나
  가중치가 없어 실제 음질·지연은 측정하지 못했다. 스트리밍 구조·끼어들기·전처리는
  실프로세스로 확인했다(첫 소리 16ms, 25% 지점 취소 시 추가 오디오 0조각).
- **한국어 전처리의 '분' 판별은 완전하지 않다.** 상담에서 시간이 압도적이라
  한자어를 기본으로 두고 사람 단서(고객·참석 등)가 가까울 때만 고유어로 읽는다.
  "다섯 분 오셨어요"를 "오 분"으로 읽을 수 있다.
- **BOT-VOICE에 LLM 기반 의도 분류가 없다.** 현재는 정규식 인텐트다. 저작 도구가
  즉시 시험할 수 있다는 장점이 있지만 표현 변형에 약하다. sLLM 분류기는
  LLM-GW를 경유해 붙일 수 있게 계약은 열어 두었다.
- **무응답 타임아웃을 발생시키는 주체가 없다.** 엔진에 ``timeout()``은 있으나
  실제 타이머는 통화 제어(CTI/SIP) 쪽에서 걸어야 하며 고객사 환경에 달렸다.
- **PyArmor 난독화는 검증되지 않았다.** 상용 도구라 이 환경에 없다. 빌드
  스크립트에 `--obfuscate`로 배선돼 있고 도구가 없으면 실패하지만, 실제 난독화
  산출물이 정상 기동하는지는 빌드 서버에서 확인해야 한다. 소스 보호가 계약
  조건인 사업에서는 이 단계를 반드시 리허설한다.
- **릴리스 검사는 정적 검사다.** 파일 트리를 훑을 뿐 실행 결과를 보지 않는다.
  "공개키가 있다"는 확인하지만 "그 키로 발급한 라이선스가 실제로 통과한다"는
  빌드 서버에서 한 번 돌려 봐야 한다(README의 검증 절차 참조).
- **Helm 차트는 렌더링까지만 검증된다.** 이 개발 환경에 K8s 클러스터가 없어
  실제 기동·프로브·볼륨 바인딩은 확인하지 못했다. K3s 단일노드 리허설이 남았고,
  그 전까지 `values.yaml`의 storageClass·accessMode는 고객사 환경에 맞춰야 한다.
- **Ingress·TLS는 껍데기만 있다.** 고객사마다 L7 구성(F5·NGINX·Apache)이 달라
  하나를 가정하면 대부분에서 못 쓴다. 구축 시 붙인다.
- **HWP 표 안의 글자는 추출되지 않는다.** 표 개체는 별도 레코드에 있어 본문
  레코드만 읽는 현재 구현으로는 안 잡힌다. 해당 문서에는 경고를 남긴다.
  표가 많은 약관은 HWPX로 받는 편이 낫다(표 내부까지 그대로 읽힌다).
- **배포용 HWP(ViewText)와 암호 문서는 읽지 못한다.** 복호화 키가 필요하므로
  원본을 요청하는 것 외에 방법이 없다 — 오류 메시지에 그렇게 적어 둔다.
- **스캔 PDF는 OCR이 없다.** 텍스트 레이어가 없으면 실패로 알린다.
  OCR 엔진은 폐쇄망 반입 대상이 하나 더 느는 일이라 고객사와 합의할 사항이다.
- **번들 빌드의 docker 경로는 CI에서만 검증된다.** `docker save`/`load`는 데몬이
  필요해 단위 테스트로 덮을 수 없다. 계획 계산·체크섬·사전 점검·무결성 대조는
  전부 테스트로 고정돼 있다.
- **`recommends`(기능 의존)는 아직 UI-AGENT→TA-ASSIST 하나뿐이다.** 다른 화면·
  블록의 기능 의존은 패키지 구성이 확정되는 대로 채운다.
- **운영 콘솔에 테넌트·사용자 관리 화면이 없다.** 현재는 조회 전용(블록 상태·
  라이선스·감사)이다. 권한 부여는 IdP/SSO 연동과 함께 설계해야 하므로 토큰 발급은
  아직 `issue_access_token`(개발용)에 머문다.
- **GPU 자원·세션 이력 위젯이 없다.** Prometheus 연동과 CORE-BUS 세션 이력 API
  확장이 선행돼야 한다.
- **해시 체인은 변조를 막지 않고 탐지한다.** root 권한자는 파일 전체를 다시 쓸 수
  있다. 완전한 방어는 head 해시를 외부에 정기 공증(일일 출력·별도 매체 보관)하는
  **운영 절차**와 함께여야 성립한다 — 기술만으로 닫히지 않는 부분이다.
- **CORE-SEC은 단일 인스턴스여야 한다.** 해시 체인은 단일 라이터를 전제한다.
  여러 인스턴스가 같은 디렉토리에 쓰면 체인이 깨진다. 감사 기록량이 한 프로세스를
  넘어서는 규모에서는 테넌트별 체인 분리가 필요하다(미구현).
- **KCMVP 검증모듈은 연동 지점만 있다.** 실제 모듈은 고객사 조달품이고 연동
  방식(PKCS#11/전용 SDK/HSM)이 벤더마다 다르다. 제공자 미지정 시 **조용히 AES로
  폴백하지 않고 오류를 낸다** — 검증모듈을 쓴다고 적어 놓고 소프트웨어 암호가
  도는 것이 이 영역에서 가장 나쁜 사고이기 때문이다.
- **감사 이벤트 생산자는 아직 세 곳이다.** CORE-BUS(세션 시작·종료),
  RAG-KB(문서 파기), SCN-STUDIO(룰 배포). 로그인·PII 원문 열람·녹취 반출은
  해당 화면이 생기는 시점(CORE-ADM)에 붙인다.
- **개발 체크아웃에서는 서명 검증이 꺼져 있다.** 공개키가 레포에 없기 때문이며,
  이 상태로 납품되면 DRM이 없는 것과 같다. 릴리스 빌드가 공개키를 내장해야 켜진다.
  CORE-LIC은 기동 시 경고를 남기고 `/internal/v1/license`의 `signature_verified`로 노출한다.
- **라이선스 폐기(revocation) 목록이 없다.** 폐쇄망은 폐기 목록을 받을 경로가
  없으므로, 계약 종료는 만료일로만 다룬다. 조기 회수가 필요하면 짧은 만료로 발급하고
  갱신하는 방식이 유일한 수단이다.
- **시간 단위 용량(`audio_hours_monthly`)은 아직 강제되지 않는다.** 동시 채널은
  CORE-BUS가 세지만, 월 누적 시간은 집계 저장소가 선행돼야 한다. 회의록 패키지를
  시간제로 파는 계약에서는 이 부분을 채워야 한다.
- **동시 채널은 CORE-BUS 단일 인스턴스를 전제한다.** Redis 정렬 집합으로 세므로
  여러 CORE-BUS가 같은 Redis를 보면 정확하지만, 세션 생성이 확인-후-등록이라
  극단적 동시 인입에서 한두 건이 상한을 넘을 수 있다. 채널 과금 특성상
  허용 오차로 두되, 엄밀함이 필요하면 Lua 스크립트로 원자화한다.
- **룰 배포는 산출물 생성까지다.** 배포 시 FLT-MICRO 형식 JSON을 만들어 주지만,
  필터 블록에 자동 반영되지는 않는다(현재는 파일 주입). API 배포는 Wave 6.

### 로컬 실행

```bash
make install          # uv 워크스페이스 동기화
make check            # 린트 + 블록 경계 + 타입 + 테스트 + 카탈로그 검증
make up && make demo  # compose 기동 후 http://localhost:8080/demo
```

`make test`는 Redis도 GPU도 요구하지 않는다(인메모리 버스 + fake 어댑터).
Redis가 떠 있으면 실프로세스 스택 스모크 테스트까지 함께 돈다.

### 블록 개발 규칙

1. **블록 간 코드 import 금지** — 공유는 `libs/` 아래 명시적으로 올린 것만 허용
   (`vai_contracts` 계약 · `vai_common` 런타임 인프라 · `vai_retrieval` 검색 인프라). CI에서 import-linter로 강제
2. **계약 우선**: 이벤트 스키마(AsyncAPI)·API(OpenAPI)를 먼저 정의 → 코드 생성. 계약 변경은 하위 호환 검사 통과 필수
3. **어댑터 플러그인**: 엔진 추가는 `adapters/`에 클래스 추가 + entry-point 등록. 코어 수정 발생 시 설계 리뷰
4. **환경 분기 금지**: `if is_onprem:` 대신 어댑터/설정 주입
5. **블록 인수 기준(DoD)**: 계약 테스트 + 단독 기동 smoke + 성능 예산(해당 시 지연 목표) 통과 → 그 시점부터 견적·청구 가능한 상태로 간주
6. **fake 어댑터 필수**: 모든 AI 엔진 블록은 결정적 fake 구현 제공 — GPU 없는 CI에서 전체 파이프라인 통합 테스트

## 3. 핵심 인터페이스 (요약)

- 이벤트 버스 토픽: `audio.in` → `audio.segment` → `stt.delta` → `filter.clean` → `assist.popup` / `session.closed` → `summary.done`
  - **Stream**(Redis Streams, 컨슈머 그룹): 위 토픽들. 타입별 스트림 1개 + 메시지의 `session_id` 필드로 세션 구분 — 세션마다 스트림을 만들면 워커가 신규 세션을 발견할 방법이 없다
  - **UI 채널**(Redis Pub/Sub): `vai:ui:{session_id}`. 접속 중인 화면으로의 팬아웃 전용 — 내구성이 불필요하고 UI 렌더 예산(<50ms)에 유리
- WebSocket `/v1/audio/stream` 프로토콜: [02 문서](02-architecture.md) §4 (사양서 원문 규격 준수)
- REST(관리): `/v1/kb/*`(지식), `/v1/sessions/*`(이력), `/v1/admin/*`(테넌트·룰셋·라이선스 상태), `/v1/rules/*`(컴플라이언스 룰셋 CRUD)

## 5. 품질·성능 검증 체계

| 항목 | 방법 |
|------|------|
| 지연 예산 회귀 | 각 블록 계약 테스트에 지연 assert(FLT<10ms, 검색<100ms, 리랭킹<80ms), 통합 p95<1초 — CI 야간 벤치 |
| STT 품질 | 도메인 오디오 평가셋(금융 상담 100통화, 회의 20건) WER/CER 회귀 측정 |

| 요약 품질 | 표준요약 골든셋 + 사람 평가 루브릭(주기 샘플링) |
| 부하 | 동시 채널 시뮬레이터(오디오 재생기) — 프로파일 S/M 사양 검증 리포트 |

### 5.1 골든셋 회귀 게이트 (`evalctl`) — 구현됨

계획만 있던 위 표 중 **모델 없이 결정적으로 돌릴 수 있는 축부터** 실제 게이트로
만들었다. `eval/`에 골든셋과 기준선이 있고 `tools/evalctl`이 채점한다.

| 스위트 | 사례 | 지표 | 판정 |
|---|---|---|---|
| `retrieval` (약관 조항 검색) | 42 | Recall@3 · MRR · nDCG@3 | 기준선 대비 하락 시 실패 |
| `pii` (마스킹) | 20 | 정확도 | 100% 미만이면 실패 |
| `tts` (한국어 수사 읽기) | 18 | 정확도 | 100% 미만이면 실패 |
| `grounding` (추천 답변 근거 검증) | 20 | 정확도 | 100% 미만이면 실패 |
| `intent` (음성봇 의도 라우팅) | 20 | 정확도 · **오라우팅 수** | 오라우팅이 늘면 실패 |

설계에서 의도적으로 정한 것들:

* **정답은 청크 ID가 아니라 조항 ID**다. 청킹 파라미터를 바꾸는 순간 골든셋
  전체가 무효가 되는 것을 막는다.
* **질의는 상담 발화체**로 쓴다("카드 잃어버렸어요 어떻게 하죠"). 검색 질의처럼
  다듬은 문장으로 재면 현장 성능이 과대평가된다.
* **top_k는 출하 설정(3)과 같게** 둔다. 10으로 올리면 점수는 오르지만 그 시스템은
  출하되지 않는다.
* **지연은 게이트가 아니다.** 러너 성능차로 매번 빨강이 뜨면 진짜 회귀도 같이
  무시된다 — 2배 초과 & 5ms 초과일 때만 경고한다.
* **사례 수 감소도 회귀**다. 실패하는 사례를 지워 초록을 만드는 것이 가장 조용한
  품질 하락 경로다.
* **알려진 한계는 따로 센다.** "한글로 읽은 주민번호는 못 잡는다"를 사례로 고정하되
  통과 건수에 섞지 않는다.

기준 수치는 모델 없는 기본 어댑터(HashingEmbedder + 어휘 리랭커) 기준이다.
로컬 임베딩 모델이 번들에 들어오면 이 수치가 올라가야 하며, **올라간다는 사실을
이 하네스가 증명한다.**

### 5.2 하네스가 즉시 찾아낸 결함 세 건

평가셋의 값어치는 "점수가 나온다"가 아니라 "그동안 안 보이던 것이 보인다"에 있다.
도입 첫날 셋이 나왔고, 셋 다 조용히 잘못 도는 종류였다.

**1. 조사가 붙은 PII가 마스킹되지 않았다** (FLT-MICRO). `010-1234-5678로`,
`900101-1234567이고`. 파이썬 정규식 `\b`는 유니코드 기준이라 숫자와 한글 사이에
경계를 만들지 않는다. 상담 STT 출력에서는 조사가 붙은 형태가 오히려 다수다 —
평가셋 없이는 계속 새고 있었을 경로다. 숫자 룩어라운드로 교체했고, 지역번호
(02·031…) 미탐도 함께 고쳤다.

**2. 하이브리드 융합이 희소 전용 히트를 버렸다** (`vai_retrieval.hybrid`).
BM25가 1위로 올린 조항이라도 밀집 상위 후보에 없으면 본문을 못 찾아 조용히
버려졌다. "카드 정지되면…"에서 `정지`라는 단어가 제8조에만 있는데 BM25 점수
2.78(2위의 4배)로 1위였고, 결과에는 나오지 않았다. **키워드로만 걸린 문서를
버리면 하이브리드 검색이 희소 축을 갖고 있을 이유가 없다.** 저장소에 청크 ID로
본문을 되가져오는 경로(`get_by_ids`)를 추가했다.

**3. 구어와 약관어가 만나지 못했다.** 고객은 "카드 잃어버렸어요"라 말하고
약관은 "분실"이라 쓴다 — 두 표현은 글자가 하나도 겹치지 않아 어휘 검색으로는
영원히 만나지 못한다. 질의 확장 사전(`vai_retrieval.lexicon`)을 넣었다.
회수 단계에만 쓰고 리랭킹에는 원문을 넘긴다(크로스 인코더는 자연스러운 문장을
전제로 학습됐다). 어휘 리랭커는 확장어가 그대로 이득이라 `accepts_expanded_query`로
스스로 성향을 밝히게 했다 — 엔진을 바꿀 때 호출부를 고치지 않기 위해서다.

측정된 효과(42건, `evalctl run --suite retrieval [--no-expand]`):

| | Recall@3 | MRR | nDCG@3 |
|---|---|---|---|
| 개선 전 | 0.929 | 0.865 | 0.872 |
| 희소 전용 히트 복구 | 0.952 | 0.889 | 0.896 |
| \+ 질의 확장 | **1.000** | **0.948** | **0.962** |

> 확장 사전 8건은 사전을 작성한 **뒤에** 추가한 신규 사례로, 골든셋에 맞춰
> 끼워 맞춘 이득이 아님을 확인하는 용도다. 그래도 이 수치가 현장 성능을
> 보장하지는 않는다 — 기본 사전은 카드 상담 어휘 기준의 출발점이고, 사업별
> 실제 상담 로그로 검증한 뒤 테넌트 사전으로 덮어써야 한다.

### 5.3 추천 답변 — 근거 없이는 한 글자도 만들지 않는다

상담원 화면에 뜬 문장은 상담원이 그대로 읽는다. 그러니 여기서 지어낸 숫자는
곧바로 고객에게 전달되고, 금융 상담에서 그것은 불완전판매다. **틀린 답변은
답변이 없는 것보다 나쁘다** — 근거 원문만 보여주면 상담원이 직접 읽고 판단하지만,
그럴듯한 오답은 그 판단 자체를 건너뛰게 만든다.

그래서 sLLM이 만든 문장을 그대로 믿지 않고, 검증을 통과한 것만 화면에 올린다
(`vai_ta_assist.answer`):

| 검사 | 무엇을 막는가 |
|---|---|
| 인용 표기 `[n]` 존재·범위 | 어느 조항을 근거로 말하는지 없으면 상담원이 확인할 방법이 없다 |
| **인용한 근거 안에 답변의 모든 숫자가 있는가** | 환각이 가장 자주·가장 위험하게 나타나는 자리. "3,000원"이 "5,000원"이 되는 것 |
| 길이 상한(140자, 두 문장) | 통화 중에 못 읽는 분량은 안 읽히고 근거 원문까지 가린다 |
| 확약 표현("반드시", "무조건") | 약관이 조건부로 쓴 내용을 무조건으로 바꿔 놓는다 |
| 어휘 일치율(20토큰 이상일 때 0.35) | 숫자는 다 맞는데 근거에 없는 문장을 통째로 지어낸 경우 |

배선에서 정한 것들:

* **근거를 먼저 띄우고 답변은 뒤따라 채운다.** 답변 생성을 기다리다 근거까지
  늦어지면 1초 예산 안에 화면에 아무것도 없다. 생성 예산(2초)은 팝업 예산과 별개고,
  넘기면 답변만 포기한다.
* **폴백으로 근거 문장을 잘라 붙이지 않는다.** 잘린 조항은 조건절이 떨어져 나가
  뜻이 바뀌는 일이 잦고, 그것은 근거를 보여주는 것보다 위험하다.
* **버스 이벤트는 최종 형태 한 번만.** 채택률 분석이 같은 팝업을 두 건으로 세면
  지표가 어긋난다.
* **답변은 자신이 인용한 근거 카드에 붙인다.** 다른 카드에 붙으면 상담원이
  엉뚱한 조항을 근거로 읽는다.

숫자 비교는 천 단위 쉼표만 지우고 소수점은 남긴다 — `3,000`과 `3000`을 다른
숫자로 보면 멀쩡한 답변을 환각으로 오판하고, `1.0%`와 `10%`를 같게 보면
완전히 다른 수수료를 통과시킨다.

`grounding` 골든셋(20건)이 이 판정을 고정한다. LLM을 부르지 않으므로 결정적이고,
**재는 것은 생성 품질이 아니라 검증기의 판단**이다 — 환각을 통과시켰는가,
멀쩡한 답변을 버렸는가. 둘 다 실패로 센다.

### 5.4 음성봇 의도 분류 — 확실하지 않으면 기권한다

정규식은 고객이 저작자가 예상한 말투로 답할 때만 맞는다. 골든셋 20건에서
**정규식만으로는 절반(10/20)**밖에 라우팅하지 못했다. 놓치면 되묻고, 두 번
되물으면 사람에게 넘어간다 — 봇이 있으나 마나 한 상태가 이렇게 만들어진다.

그렇다고 아무 갈래나 고르게 하면 더 나쁘다. **되묻기는 고객이 다시 말하면
회복되지만, 오라우팅은 엉뚱한 안내를 끝까지 듣고 나서야 드러난다.** 그래서
정확도 옆에 `misroutes`를 따로 세고, 그 숫자가 늘면 정확도가 같아도 회귀로 본다.

세 단계로 둔다. 순서가 곧 비용 순서이고, 앞이 답하면 뒤는 호출되지 않는다.

| 단계 | 비용 | 역할 |
|---|---|---|
| 정규식 | 0ms · 결정적 | 저작자가 선언한 우선순위가 그대로 이긴다 |
| 예시 발화 어휘 유사도 | 모델 없음 | 저작자가 적어 둔 예시와 가장 닮은 갈래. GPU 없는 프로파일에서도 돈다 |
| sLLM (기본 꺼짐) | 통화당 GPU | 위 둘이 기권했을 때만 — **되묻게 될 발화에서만** 비용을 낸다 |

측정된 효과(20건, `evalctl run --suite intent [--no-expand]`):

| | 정확도 | 오라우팅 |
|---|---|---|
| 정규식만 | 0.500 | 0 |
| \+ 예시 어휘 분류 | **0.900** | **0** |

설계에서 정한 것들:

* **분류기는 경로를 만들어 낼 수 없다.** 출력이 노드에 선언된 인텐트 이름인지
  엔진이 다시 확인한다. 그대로 믿고 라우팅하면 시나리오 검증이 보장하던 것 —
  도달 가능한 handoff, 갈래별 다음 노드 — 이 전부 무의미해진다.
* **기권할 길을 프롬프트에 넣는다.** 선택지에 '모름'이 없으면 모델은 반드시
  무언가를 고르고, 그게 오라우팅이 된다.
* **1등과 2등이 붙어 있으면 기권한다.** 그것은 "둘 중 하나"이지 "이것"이 아니다.
* **예시를 늘릴수록 불리해지면 안 된다.** 예시를 한 덩어리로 합쳐 비교하면
  성실하게 적을수록 점수가 떨어진다 — 예시 하나하나와 비교해 가장 닮은 것을 쓴다.
* **정규식이 맞힌 발화는 분류기에 태우지 않는다.** 저작자가 순서로 표현한
  우선순위가 흔들린다.
* **분류 예산 600ms.** 넘기면 포기하고 되묻는다. 늦은 정답보다 제때의 되묻기가
  낫고, 침묵이 길어지면 고객은 전화가 끊긴 줄 안다.

> 유사도 임계값(0.20)과 여유(0.09)는 이 20건으로 잡은 값이다. 표본이 작아
> 일반화를 보장하지 못하며, 그래서 실패가 **기권 쪽으로 기울도록** 잡았다.
> sLLM 계층이 존재하는 이유가 이것이다 — 어휘 분류는 여기까지다. sLLM의
> 실제 기여는 가중치가 있어야 측정되며, 재현되지 않는 수치는 회귀 게이트에
> 넣지 않는다.
