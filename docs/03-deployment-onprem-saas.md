# 03. 배포 전략 — 온프레미스 / SaaS 하이브리드

## 1. 배포 형태 개요

| | SaaS | 온프레미스 |
|---|------|-----------|
| 인프라 | 링버스 운영 클라우드(K8s) | 고객사 K8s 또는 제공 어플라이언스 구성 |
| 네트워크 | 인터넷 | 망분리(인터넷 차단) 전제 |
| LLM | 상용 API (Claude 등) | 로컬 vLLM (GPU 노드) |
| 업데이트 | 무중단 롤링, 주 단위 | 분기 릴리스 번들, 고객 변경관리 절차 준수 |
| 데이터 | 링버스 관리(암호화) | 고객사 내부에서만 존재 |
| 운영 주체 | 링버스 SRE | 고객사 운영팀 + 링버스 기술지원 |

**공통 원칙**: 두 형태 모두 동일한 컨테이너 이미지와 동일한 Helm 차트를 사용한다.
환경 차이는 `values-saas.yaml` / `values-onprem.yaml` 및 Provider 설정으로만 표현한다.

## 2. 패키징 구조

```
deploy/
├── charts/visionai/          # 단일 우산(umbrella) Helm 차트
│   ├── Chart.yaml
│   ├── values.yaml           # 공통 기본값
│   ├── values-saas.yaml      # SaaS 오버레이 (멀티테넌트, 외부 LLM)
│   ├── values-onprem.yaml    # 온프렘 오버레이 (단일 테넌트, vLLM, 에어갭)
│   └── charts/               # 서브차트: api-core, ai-orchestrator, knowledge-worker,
│                             #          postgresql, redis, minio, vllm(onprem only)
├── airgap/                   # 에어갭 설치 도구
│   ├── images.txt            # 필요 이미지 목록 (버전 고정)
│   ├── bundle.sh             # 이미지 tar 번들 생성
│   └── install.sh            # 내부 레지스트리 push + helm install
└── compose/                  # PoC/데모용 docker-compose (GPU 1대 규모)
```

- 서브차트 중 DB/Redis/MinIO는 **온프렘에서만 기본 활성화**. SaaS는 매니지드 서비스(RDS 등) 사용
- PoC 단계 진입장벽을 낮추기 위해 **docker-compose 단일 서버 구성**을 별도 유지 (GPU 서버 1대로 데모 가능)

## 3. 온프레미스 설치 (에어갭)

금융권 망분리 환경 = 외부 인터넷 접근 불가를 기본 전제로 한다.

### 3.1 설치 절차

1. **번들 생성** (링버스 측, 인터넷 환경): 컨테이너 이미지 + Helm 차트 + LLM 모델 가중치 + 임베딩 모델을 단일 아카이브로 패키징. 전체 해시 서명 포함
2. **반입**: 고객사 반입 절차(보안성 검토, 매체 검사)에 따라 전달
3. **설치**: `install.sh`가 내부 레지스트리에 이미지 적재 → Helm 설치 → 초기 관리자 계정/라이선스 활성화
4. **검증**: 셀프 진단 잡(smoke test) — LLM 추론, 임베딩, DB, 스토리지 왕복 확인 리포트 출력

### 3.2 온프레미스 표준 사양 (프로파일)

| 프로파일 | 용도 | GPU | 서버 구성 |
|----------|------|-----|-----------|
| **S** (PoC/소형) | 동시 세션 ~50 | L4/A10 1장 (소형 모델) | 앱+DB 통합 2노드 |
| **M** (표준) | 동시 세션 ~300 | A100/H100 1~2장 (30B급) | 앱 3노드 + GPU 1노드 + DB HA |
| **L** (대형) | 동시 세션 1000+ | GPU 4장+ (70B급/다중 모델) | 풀 HA, 스토리지 이중화 |

- 사양서는 영업 단계에서 고객사 인프라팀에 제시하는 공식 문서로 관리 (구매 리드타임이 길어 조기 제시 필수)

### 3.3 업데이트 전략

- **분기 릴리스 트레인**: 온프렘은 분기별 안정화 릴리스(LTS 성격)만 제공. 핫픽스는 보안/치명 결함에 한정
- DB 마이그레이션은 전방 호환(expand-contract) 패턴 — 롤백 가능성 보장
- 업데이트도 에어갭 번들 방식 동일. 버전 스킵 업그레이드(N-2 → N) 지원

## 4. SaaS 운영 구조

- 단일 리전 시작(국내 클라우드 리전) → 금융 고객 대응 시 별도 "금융존" 클러스터 분리 옵션
- CI/CD: main 브랜치 → 스테이징 자동 배포 → 프로덕션 승인 배포. 이미지 태그는 온프렘 릴리스와 동일 체계(SemVer)
- 테넌트 프로비저닝: 관리자 API로 수 분 내 신규 테넌트 개통(셀프서비스 가입은 후순위)
- 사용량 계측: LLM 토큰/세션 단위 미터링 → 청구 데이터 export

## 5. 라이선스 관리

| 항목 | 방식 |
|------|------|
| SaaS | 구독 상태 = DB 레코드. 시트 수·세션 쿼터 초과 시 소프트 제한(알림) → 하드 제한 |
| 온프레미스 | **오프라인 서명 라이선스 파일**(만료일, 시트 수, 활성 모듈, 고객 식별자). 앱 기동 시 공개키로 검증. 전화 홈(call-home) 없음 — 망분리 환경에서 외부 통신 시도 자체가 감점 요인 |
| 만료 처리 | 유예기간(30일) 경고 → 신규 세션 제한. 기존 데이터 접근은 차단하지 않음(고객 신뢰) |
| 모듈 게이팅 | 음성(Phase 2)·아바타(Phase 3)는 라이선스 플래그로 활성화 — 업셀 시 파일 교체만으로 개통 |

## 6. 관측성과 원격 지원

- 스택 표준: OpenTelemetry(트레이스/메트릭/로그) → SaaS는 중앙 수집, 온프렘은 고객사 내 Prometheus/Grafana 번들 제공
- 온프렘 장애 지원: 외부 접속이 불가하므로 **진단 번들 export** 기능 제공 — 개인정보 제거된 로그·메트릭·설정 스냅샷을 파일로 추출해 반출 절차로 전달받는 워크플로우
- AI 품질 모니터링: 근거 인용률, 상담원 전환율, 사용자 피드백(도움됨/안됨)을 표준 대시보드로 온프렘에도 동일 제공

## 7. 환경 차이 매트릭스 (구현 체크리스트)

코드에서 환경 분기가 필요한 모든 지점을 이 표로 관리한다. 여기 없는 분기는 만들지 않는다.

| 관심사 | SaaS | 온프렘 | 추상화 지점 |
|--------|------|--------|-------------|
| LLM | Claude API | vLLM 로컬 | `LLM_PROVIDER` |
| 임베딩 | API 또는 자체 서빙 | 로컬 임베딩 모델 | `EMBEDDING_PROVIDER` |
| 오브젝트 스토리지 | S3 | MinIO | S3 호환 API (분기 없음) |
| 인증 | 자체 IdP + 소셜(옵션) | 고객사 SSO(SAML/OIDC) 연동 | `AUTH_PROVIDER` |
| 알림(메일/SMS) | 외부 발송 서비스 | 고객사 SMTP/내부 게이트웨이 | `NOTIFIER` |
| 과금 미터링 | 활성 | 비활성(라이선스 기반) | `BILLING_ENABLED` |
| 텔레메트리 | 중앙 수집 | 로컬 수집만 (외부 전송 금지) | `TELEMETRY_EXPORT` |
| 카카오 등 외부 채널 | 활성 | 기본 비활성(DMZ 경유 옵션) | 채널 플러그인 |
