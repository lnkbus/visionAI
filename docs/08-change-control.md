# 08. 변경 통제와 시점 관리

> 두 가지를 정한다. **무엇을 PR로 올리는가**(변경 통제)와 **"그때 뭘 납품했나"에
> 어떻게 답하는가**(시점 관리). 둘 다 문서로만 적으면 지켜지지 않으므로 각각
> CI 게이트를 붙였다.

## 1. 왜 전부 PR로 하지 않는가

PR은 그 자체로 가치가 없다. **자동 검사가 붙을 지점**, **사람이 읽을 diff**,
**되돌릴 단위**가 가치다.

모든 변경에 PR을 요구하면 오탈자 수정에도 PR을 만들게 되고, 곧 아무도 diff를
읽지 않는다. 규칙이 형식이 되는 순간 **정작 중요한 변경에서도 지켜지지 않는다.**
그래서 목록을 좁게 유지한다.

반대로 전부 직접 커밋이면 인증 심사가 요구하는 변경 통제 근거가 남지 않고,
형상이 바뀐 이유를 몇 달 뒤에 커밋 메시지만으로 복원해야 한다.

## 2. 규칙

| 무엇 | 어디로 |
|---|---|
| 기능 개발, 버그 수정, 리팩터링, 문서, 테스트 | **`main` 직접 커밋** |
| `.github/change-control-paths.txt`에 걸리는 경로 | **PR 필수** |

직접 커밋 전에 로컬에서 `make check`를 돌린다. 그것이 직접 커밋의 대가다.

통제 대상은 세 기준으로 고른다:

1. **인증 심사가 변경 통제 근거를 요구하는 것** — 형상 명세, 블록 매니페스트, Helm 템플릿
2. **틀리면 되돌리기가 비싼 것** — 라이선스, 암호, 감사 로그, 지문, 인증/인가, 릴리스 빌드
3. **게이트 자신** — 워크플로, 통제 목록, 파이썬 고정. 검사를 우회하는 변경이 검사 없이 들어가면 안 된다

목록에 한 줄을 더하는 것은 "이 경로는 diff가 리뷰에 남아야 한다"는 판단이다.
그 판단 자체도 PR을 거친다(3번 기준).

### 기계가 강제한다

`main`에 push가 들어오면 CI의 `변경 통제` 잡이 본다:

- 병합 커밋(부모 2개)이면 → PR을 거친 것이므로 통과
- 부모가 하나인데 통제 경로를 건드렸으면 → **실패**, 어느 파일인지 나열

`tests/test_change_control.py`가 목록 자체를 검사한다 — 유령 항목이 없는지,
목록이 너무 넓어지지 않았는지, 워크플로가 이 파일을 실제로 읽는지.
목록이 유령을 가리키면 게이트는 통과만 하고 아무것도 막지 않는데,
그 사실은 막았어야 할 변경이 들어간 뒤에야 드러난다.

### 브랜치 보호는 걸지 않는다

`main`에 "CI 통과 필수"를 걸면 직접 push가 전부 막혀 혼합 정책이 성립하지
않는다. 대신 **`main`이 빨간불이면 다른 일보다 먼저 고친다**를 규율로 둔다.
하루 이상 빨간 채로 두면 그 다음부터 아무도 CI를 보지 않는다.

## 3. 시점 관리

온프렘 제품에서 **"3월에 저 고객사가 받은 게 정확히 무엇인가"**에 답하지 못하면
장애 대응이 성립하지 않는다. 고객사는 자기가 언제 무엇을 받았는지 모르고,
우리도 그 시점의 코드를 되짚을 수 없다.

버전 문자열만으로는 부족하다. `0.3.0`을 표방하는 서로 다른 물건이 생길 수
있다는 것이 형상 관리의 출발점이었다(docs/07 §2). 그래서 **시점마다 형상 해시를
함께 박제**한다.

```bash
make snapshot VERSION=0.2.0 NOTE="AICC 파일럿 납품본"          # 미리보기
make snapshot VERSION=0.2.0 NOTE="AICC 파일럿 납품본" WRITE=1   # 기록
git tag v0.2.0 && git push origin v0.2.0
```

기록되는 것 (`deploy/release/history.yaml`):

| 항목 | 왜 |
|---|---|
| 버전 · 날짜 | 사람이 부르는 이름 |
| **깃 커밋(40자리)** | 코드로 되돌아가는 유일한 좌표. 짧은 해시는 언젠가 충돌한다 |
| 패키지 4종 형상 해시 | 납품본과 한 줄로 대조 |
| 블록별 버전 | "그때 STT는 몇이었나" |

`snapshot`은 **형상 명세와 어긋난 상태를 박제하지 않는다.** 어긋난 채로 기록하면
이력이 거짓이 되고, 거짓인 이력은 없느니만 못하다.

### 이력은 append-only

지난 항목은 고치지 않는다. `blockctl history`(CI 게이트)가 검사하는 것:

- 버전 중복 — 같은 이름의 서로 다른 물건이 생긴다
- 버전·날짜 역행 — 이력 순서가 깨진다
- 40자리 커밋 해시, 64자리 형상 해시 — 좌표가 흔들리면 이력이 아니다

### 버전을 언제 올리나

| 무엇이 바뀌었나 | 어디를 올리나 |
|---|---|
| 블록 하나의 동작 | 해당 `blocks/*/block.yaml`의 `version` |
| 납품 시점 | `snapshot` + `git tag` |
| 계약·API 호환성이 깨짐 | 블록 major, 릴리스 minor 이상 |

블록 버전과 릴리스 버전은 별개다. 블록 단위로 떼어 파는 제품이라 고객사마다
받은 블록 조합이 다르고, 그래서 이력에 **블록별 버전을 함께** 적는다.

## 4. 되돌리기

| 상황 | 방법 |
|---|---|
| PR로 들어온 기능 하나 | 병합 커밋 하나를 `git revert -m 1` |
| 직접 커밋 하나 | `git revert <커밋>` |
| 특정 납품 시점으로 | `history.yaml`에서 커밋을 찾아 `git checkout` |
| 고객사 설치본이 무엇인지 확인 | 설치본의 형상 해시를 `history.yaml`과 대조 |

되돌린 뒤에는 형상 명세가 어긋난다. `blockctl freeze <패키지> --write`로 맞추고
그 diff를 PR에 남긴다 — 되돌리기도 형상 변경이다.

## 5. 요약

| 게이트 | 무엇을 막나 | 언제 도나 |
|---|---|---|
| `변경 통제` 잡 | 통제 경로가 PR 없이 들어오는 것 | `main` push |
| `tests/test_change_control.py` | 통제 목록이 유령을 가리키거나 넓어지는 것 | 매 커밋 |
| `blockctl history` | 이력이 깨지는 것 | 매 커밋 |
| `blockctl freeze` | 형상이 조용히 어긋나는 것 | 매 커밋 |
| `blockctl snapshot` | 어긋난 상태가 박제되는 것 | 릴리스 시 |
