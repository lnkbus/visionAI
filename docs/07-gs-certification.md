# 07. GS인증 준비 — 회의록 패키지 형상 고정

> 대상: **패키지 B — 스마트 회의록** (`values-meeting.yaml`)
> 이 문서는 인증 신청 실무의 준비 상태를 정리한다. **아직 신청하지 않았고,
> 시험 결과도 없다.** 무엇이 기계로 보장되고 무엇이 사람 손을 기다리는지를
> 구분하는 것이 이 문서의 목적이다.

## 1. 왜 회의록 패키지부터인가

GS인증은 공공 조달에서 사실상의 입장권이다(중소기업자간 경쟁제품 지정, 수의계약
근거, 우선구매 대상). 회의록 패키지를 먼저 올리는 이유는 **인증 범위가 가장
좁게 떨어지기 때문**이다:

- 외부 연동이 없다. AICC는 고객사 교환기·CTI와 붙어야 시험이 성립하지만,
  회의록은 오디오 파일과 브라우저만으로 전 기능을 시연할 수 있다.
- 개인정보 처리가 상대적으로 단순하다. 상담 녹취와 달리 회의 음성은 참석자
  동의 절차가 명확하다.
- 화면이 하나다(`UI-MEET`). 시험 케이스가 화면 단위로 정리된다.

AICC 패키지는 회의록 인증을 받은 뒤 **범위 확대**로 가는 편이 빠르다.

## 2. 형상 식별 — 기계가 만든다

인증 심사에서 가장 먼저 요구되는 것은 기능이 아니라 **형상 식별**이다:
이 제품이 정확히 어떤 구성요소의 어떤 버전으로 이루어져 있는가, 그리고 제출본과
현장 설치본이 같은가.

손으로 적은 구성요소 목록은 반드시 어긋난다. 블록 하나를 올려도 문서는 그대로
남고, 그 사실은 심사 당일이나 현장 검수에서 드러난다. 그래서 명세를 **카탈로그와
Helm 오버레이에서 계산**한다.

```bash
blockctl freeze meeting            # 기록본과 대조 (CI 게이트, 다르면 exit 1)
blockctl freeze meeting --write    # 의도한 변경을 반영하고 diff를 리뷰에 남긴다
```

산출물: `deploy/release/packages/meeting.yaml`

| 항목 | 왜 넣는가 |
|---|---|
| 구성요소 ID·이름·버전 | 형상 식별의 기본 |
| **소스 해시** | 버전 문자열은 사람이 올려 주지 않으면 안 바뀐다. **버전은 그대로인데 내용이 다른 상태**가 형상 관리에서 가장 위험하다 — 같은 버전을 표방하는 두 개의 다른 물건이 생긴다 |
| 라이선스 게이트 키·청구 단위 | 납품 범위와 계약 범위 대조 |
| 인프라 이미지 | 반입 대상 전체. 하나 빠지면 폐쇄망에서 기동하지 않는다 |
| 전체 형상 해시 | 제출본과 설치본을 한 줄로 대조 |

타임스탬프는 넣지 않는다. 넣으면 내용이 하나도 안 바뀐 실행에서도 파일이 달라져,
diff가 "형상이 실제로 바뀌었는가"를 말해 주지 못한다.

`tests/`는 해시 대상에서 뺀다. 납품물에 들어가지 않고, 테스트만 고쳐도 형상이
바뀌었다고 하면 그 신호는 곧 무시된다.

## 3. 준비 상태

### 3.1 기계로 보장되는 것 (CI가 매 커밋 검사)

| 심사 항목 | 무엇으로 | 상태 |
|---|---|---|
| 형상 식별·변경 통제 | `blockctl freeze` + CI 대조 | ✅ |
| 구성요소 정합성(의존·토픽·청구 단위) | `blockctl check` | ✅ |
| 모듈 경계·계층 | `import-linter` 4개 계약 | ✅ |
| 기능 시험 | `pytest` 745건 | ✅ |
| 상태 영속성·자원 회수 | `tests/test_state_durability.py`·`test_session_cleanup.py` | ✅ |
| 품질 회귀(정확도) | `evalctl compare` 골든셋 5종 | ✅ |
| 배포 형상 렌더링 | `helm lint` + 오버레이 5종 템플릿 | ✅ |
| 배포 매니페스트 **스키마 적합성** | `kubeconform`(k8s 1.29 strict) | ✅ |
| 보안 — 개인키 유출 | `blockctl release-check` | ✅ |
| 감사 로그 무결성 | 해시 체인 + 검증 API | ✅ |

### 3.2 사람 손이 필요한 것 (미완)

| 항목 | 왜 아직인가 |
|---|---|
| **사용자 매뉴얼·설치 매뉴얼** | 심사 필수 제출물이다. 화면 캡처가 필요해 실기동 환경이 선행한다 |
| **요구사항 명세서 ↔ 시험 케이스 대응표** | 시험 케이스는 있으나(`pytest`), 심사가 요구하는 형식의 추적표로는 정리되지 않았다 |
| **K8s 단일노드 실기동 리허설** | **GPU가 필요 없다는 것을 확인해 노트북으로 옮겼다**(`docs/09`). arm64 이미지가 붙어 Apple Silicon에서 밟을 수 있다. 렌더링과 스키마 적합성까지는 CI가 검증하고(오버레이 5종·211개 리소스), 남은 것은 실제 스케줄링·PVC 바인딩·프로브 통과다 — 절차는 있고 아직 밟지 않았다 |
| **성능 시험 결과** | 동시 채널 시뮬레이터로 프로파일 S/M을 측정해야 한다. GPU 환경 필요 |
| **화자분리 정확도 근거** | 기본 spectral 임베더는 음역이 뚜렷이 다른 화자만 가른다. 심사 시연 품질을 내려면 신경망 임베더 반입과 임계값 재조정이 선행한다 |
| **STT 품질 근거(WER/CER)** | 오디오 평가셋과 로컬 모델 가중치가 필요하다. 현재 골든셋은 텍스트 경로만 덮는다 |
| **PyArmor 난독화 검증** | 배선만 돼 있고 상용 라이선스가 필요해 미검증이다 |

> 3.2의 항목들은 코드로 해결되지 않는다. 인증 일정을 잡을 때 **여기가 임계
> 경로**이며, 특히 매뉴얼과 성능 시험은 실기동 환경 확보에 종속된다.

## 4. 형상 변경 절차

1. 코드·구성 변경을 커밋한다.
2. CI가 `blockctl freeze meeting`으로 대조한다 — 어긋나면 실패한다.
3. 의도한 변경이면 `blockctl freeze meeting --write`로 갱신하고 **그 diff를
   리뷰에 포함**한다. 형상 변경이 조용히 지나가지 않게 하는 것이 이 절차의 전부다.
4. 인증 후에는 형상 해시가 곧 인증 범위다. 해시가 바뀌면 변경 신고 대상인지
   먼저 판단한다.
